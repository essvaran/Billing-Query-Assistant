# Closed failure-to-test loop

Generated by `scripts/closed_loop_report.py`. All data is synthetic.

## 1. The failure, found in traces

In the full-system run (production model, 39 cases) **6 of 25 answerable cases cited the wrong source** (RAN02, RAN06, RAN10, RAN14, RAN19, RAN20): three cited a near-identical sibling article, one cited an internal Zendesk macro to a customer and invented steps that were in no source (RAN14), one cited the shipping matrix instead of the delivery article. One status ticket escalated after about 11,500 tokens of searching (RAN10). Traces for these cases: the `after` rows of `python scripts/taxonomy_tally.py after fix1` (`taxonomy.md` now shows the `fix1` run).

## 2. The failure is already a test

Each of those is a case in `evaluation/integrated/cases.jsonl` with the assertion `cites_gold_source`, so the suite was red on them. A failure an agent reports from the UI becomes a permanent case the same way: Report wrong answer, then Review inbox, then Create evaluation case (`tier1/eval_cases.py`; checked in a browser, and by `tests/test_tier1_api.py`).

## 3. Two fixes, each with a reason

- **Internal macros are excluded from customer-facing search.** They are agent templates, not documents a customer should be pointed at, and stale text hides in them: an old macro quoting the retired 14-day window is how the original refund escalation happened.
- **The prompt tells the model to put the ticket's error code in its search query**, because an error code identifies the one article that explains it.

## 4. Measured on tickets the fixes were not derived from

15 held-out tickets (FAQ, order status, delivery time), a different random draw from the main suite, none of them seen while finding the problem. Same cases, same model, same code; the only difference is the two fixes switched off or on (`TIER1_ABLATE=macro_filter,error_code_prompt`). **The model here is `openai/gpt-oss-20b`, not the production `gpt-oss-120b`**, because the production model's 200,000-token daily cap was spent by the time this was run (`seams.md` 44). So this shows whether the fixes help, not what the production system scores.

## 6. How far to trust this

- **n = 15 and one run each.** A difference of one or two cases is inside what run-to-run variation could produce; variance is not measured (a rerun with `LLM_CACHE=off` twice would measure it).
- **Weaker model.** If `gpt-oss-20b` fails mostly for reasons unrelated to source choice (for example citation format), the comparison has little room to move: read the failure reasons in the two reports before reading the totals.
- The first full re-run on the production model (2026-10-16) did not complete (6 of 39 cases before the daily cap) and was discarded; the `fix1` run in section 5 is a later, complete run.
- The judges are not used here (assertions only), and neither has been validated against a human yet.
- **Run-to-run variance is larger than these differences.** An uncached rerun of 10 of the `fix1` cases (`latency10`) passed 4 of 10, against 7 of 10 in `fix1` (flipped: RAN05, RAN07, RAN09). A before-and-after difference of three cases can come from the draw alone.
- The corpus is synthetic and templated; real near-duplicate articles may behave differently.
