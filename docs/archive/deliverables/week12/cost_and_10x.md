# Cost per deflected ticket and the 10x plan

Generated by `scripts/cost_and_10x.py` from the eval run `fix1` (39 cases, entitlement check and first search prefetched in code). Corpus and tickets are synthetic.

## Cost per deflected ticket

- Total model spend across the 39-case run: **$0.021045** (agent plus guards; the judge is eval-only and excluded)
- Deflected tickets (answered and every assertion passed): **23**
- **Cost per deflected ticket: $0.000915**. This divides ALL spend, including tickets that escalated, by deflected tickets only, so escalations are charged to the ones that succeeded.
- A ticket that reaches the model costs about $0.00082 (4,161 tokens over 1.7 model calls on average).
- 20% of the random sample never reaches a model (the pre-guard escalates legal, safety, fraud and injection text for free).
- Prices used: $0.15 in and $0.6 out per million tokens for openai/gpt-oss-120b, from the catalog's model prices (https://console.groq.com/docs/models, checked 2026-10-18). Free-tier usage is not billed; these are the paid on-demand rates.

## What breaks first at volume

Three provider limits apply to this model on the free tier. Two come from response headers; the third is **not in any header** and was found the hard way:
after a day of testing, requests started failing with `tokens per day (TPD): Limit 200,000, Used 199,313`.

| Limit | Value | Source |
|---|---|---|
| Tokens per minute | 8,000 | response header |
| Requests per day | 1,000 | response header |
| **Tokens per day** | **200,000** | error body of a 429 on 2026-10-16 |

Per ticket that reaches a model: 4,161 tokens and 1.7 requests. Model-ticket share: 80% (random sample, n=20).
ASSUMPTION: 15% of a day's tickets arrive in the busiest hour.

| Scenario | Tickets/day | Tokens/day (limit 200,000) | Requests/day (limit 1,000) | Peak tokens/min (limit 8,000) | Monthly spend | First to break |
|---|---|---|---|---|---|---|
| Today (2,000 per month) | 67 | 221,923 (111%) | 90 (9%) | 555 (7%) | $1.31 | tokens per day (1.1x over) |
| 10x (20,000 per month) | 667 | 2,219,233 (1110%) | 900 (90%) | 5,548 (69%) | $13.06 | tokens per day (11.1x over) |
| Black Friday week (20,000 in 7 days) | 2,857 | 9,511,000 (4756%) | 3,857 (386%) | 23,778 (297%) | $55.98 | tokens per day (47.6x over) |

**Answer: the daily token limit breaks first, and it is already below today's volume.** It caps the system at about **60 tickets a day** (1,802 a month), against 67 a day today. The daily request limit would allow about 741 a day and the per-minute limit about 961 a day at peak, so those matter only after the token limit is lifted. Money is not the problem: spend stays in single dollars at every scenario above.

This is not hypothetical. This 39-case evaluation run used 109,910 agent tokens (the judges run on a different model with its own limit). On 2026-10-16 one run plus a few experiments exhausted the day's allowance and a later run failed halfway; the evaluation now stops, keeps the finished cases and continues with `--resume` instead of recording the failures as if they were the system's (`seams.md` 44).

Steady-state speed: at 4,161 tokens per model ticket (random sample; the whole 39-case suite averages 3664 because many of its cases are short) the per-minute limit allows **1.92 tickets per minute**, which is why back-to-back tickets queue behind the limiter (p50 latency 57.1 s, p95 120.1 s, from the `latency10` run: 9 model tickets back to back with the response cache off (18 model calls, none cached), first ticket excluded).

## What to do about it, ranked by impact

| # | Change | Effect | Cost and risk |
|---|---|---|---|
| 1 | Move off the free tier (the provider's error message points to its paid Dev Tier) | Lifts all three limits. The paid limits are NOT measured here, so size them before promising a number | Money; check the price table in `src/generation/cost.py` first |
| 2 | DONE in this run: the entitlement check and first search run in code before lap 1 (prefetch), and the model keeps every tool for anything else | Measured here: 4,161 tokens and 1.7 model calls per model ticket. Compare the `after` run (no prefetch) and `docs/archive/deliverables/week12/eval/report_pf10_*.md` for a 10-ticket A/B | The model no longer chooses those two calls, so the report measures tool choice on the calls it still makes |
| 3 | Shorter system prompt and search snippets cut from 700 to about 400 characters | Fewer tokens per ticket | Quality risk: re-run the eval |
| 4 | Queue tickets with a small worker pool and show 'working' in the UI | A burst becomes waiting instead of failures. Does NOT raise the daily token cap | A day of work; a real queue (Redis or similar) once there is more than one process |
| 5 | Cache answers to repeated questions | Unknown share of repeats in real traffic: not measured | Staleness: must be invalidated when a policy document changes |

Not measured: real concurrency behaviour, paid-tier limits, provider-side prompt caching and the real share of repeated questions.
