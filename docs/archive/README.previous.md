# Billing Support RAG

A production-ready Retrieval-Augmented Generation (RAG) system for answering billing questions and resolving support tickets. Supports both a conversational RAG chat interface and an agentic ReAct loop that resolves tickets by calling structured tools via the Model Context Protocol (MCP).

---

## Tier-1 Deflection Assistant (Week 12 capstone)

An integrated support assistant: it answers Tier-1 tickets from the help centre with a citation that names the
refund-policy version it used, checks the customer's real entitlement through a tool before saying anything about
refunds or shipping, and escalates to a person instead of guessing. **All data in this project is synthetic**
(generated by `scripts/generate_synthetic_corpus.py`); no real client content is included.

One entry point, `tier1.service.handle_ticket`, serves the Angular workspace, the CLI and the eval suite, so the evals
grade exactly what an agent sees.

### Who sees what

- **Any signed-in user:** the chat page only. **Docs** mode searches the help centre. **Agent** mode runs the Tier-1
  assistant as the user's OWN customer account, matched on the sign-in email (live steps, cited answer, Copy reply,
  Report wrong answer). A user with no linked customer account cannot use Agent mode.
- **Admin only:** the "act as customer" picker. With the synthetic data nobody signs in with a customer's email, so for a
  demo set `TIER1_DEMO_CUSTOMER_ID=C1000` (leave it unset in production).
- **Admin (`ADMIN_EMAIL`):** also the ticket queue and review, Try a ticket, **Escalations** (list, claim, resolve,
  manual escalate), Insights, traces, review inbox, regression runs, **Label replies** (human labels for judge
  agreement) and eval runs. These are blocked for users in the API (403) and the UI (a page says why).
- **Help** in the header shows the user guide (`docs/USER_GUIDE.md`) filtered to your role.
- Both themes (dark and light, toggle in the header) cover every page, and the layout works on a phone.

### Quick start: one command

You need Python 3.12 and a free Groq API key (and Node 22 for the web app).

```bash
python -m venv .venv && source .venv/bin/activate        # Windows: .venv\Scripts\activate
make up                                                  # Windows: ./tasks.ps1 up    Without make: python -m tier1 up
```

The first run creates `.env` from `.env.example` and stops with the list of values to fill in (`GROQ_API_KEY`,
`JWT_SECRET` of 32+ characters, `ADMIN_EMAIL`). Run it again: it checks the key and the models it can reach, installs
packages, generates the synthetic data, builds the search index, loads the ticket database and answers one random
ticket. Every stage prints OK, SKIP or FAIL with the fix, and a re-run skips what is done.

Other commands:

```bash
python -m tier1 demo                         # answer a random ticket; the seed is printed so you can repeat it
python -m tier1 answer --ticket TK3000       # one ticket from the sample
python -m tier1 eval --tag fix1              # the full integrated eval suite; --resume continues after the daily cap
python -m tier1 eval --rescore fix1          # recompute the report and judge agreement, no model calls
python scripts/mcp_smoke.py                  # talk to both MCP servers the way an outside client would
python -m pytest tests -q                    # tests (the ones needing the search index skip until you run make up)
```

The web app (two terminals):

```bash
make api                                     # FastAPI on :8000; GET /api/ready says whether it can answer tickets
cd frontend && npm ci && npx ng serve --proxy-config proxy.conf.json    # Angular on :4200
```

Sign in with Google or email and password; the `ADMIN_EMAIL` account is the team lead. Or run everything with
`docker compose up --build` and open http://localhost:8080. Compose runs the API with `APP_ENV=production`, which
refuses to start (naming each fix) on unsafe settings; the images have not been built on this machine yet.

How to use each screen, by role: `docs/USER_GUIDE.md` (also in the app under **Help**).

### Sharing the app with ngrok (a demo, or a reviewer on another machine)

ngrok gives your local app a public https address. Use it for a live demo or to let a reviewer from another squad open the UI
without installing anything. Tested here: the ngrok install and config (v3.39) and the dev-server host setting. Not tested: a live
public tunnel, because opening one exposes the app to the internet and that is your call.

**One-time setup**

1. Install ngrok (https://ngrok.com/download) and create a free account.
2. Save your auth token on your machine (copy it from the ngrok dashboard; never put it in the repo or in `.env`):
   ```bash
   ngrok config add-authtoken <your-token>
   ```

**Every time (three terminals)**

```bash
make api                                                     # 1. the API on :8000
cd frontend && npx ng serve --proxy-config proxy.conf.json   # 2. the UI on :4200 (it proxies /api to :8000)
ngrok http 4200                                              # 3. the tunnel
```

Only the UI needs a tunnel: the browser talks to the Angular dev server, which forwards `/api` to the API on your machine.
Copy the `https://....ngrok-free.dev` address that ngrok prints and open it.

If you run the Docker setup instead (`docker compose up --build`), tunnel its web port: `ngrok http 8080`. The nginx container
already forwards `/api`.

**Three things that commonly go wrong**

- **Google sign-in fails ("origin not allowed").** Add the ngrok address under *Authorized JavaScript origins* for your OAuth client
  (Google Cloud Console, APIs and Services, Credentials) and wait a minute. A free ngrok address changes on every run, so either
  repeat this each time or reserve your free static domain in the ngrok dashboard and start the tunnel with
  `ngrok http --url=<your-domain>.ngrok-free.dev 4200`.
- **The dev server refuses the request with a "host not allowed" message.** `frontend/angular.json` already allows `.ngrok-free.dev`.
  For any other ngrok domain, add it to `allowedHosts` there, or run `npx ng serve --proxy-config proxy.conf.json --allowed-hosts <your-host>`.
- **A warning page appears first.** On the free plan ngrok shows an interstitial the first time a browser visits; click *Visit Site*.
  A reply from the assistant can take up to a minute on the free model tier, so a slow first answer is normal.

**Before you share the link**

- Anyone who can reach the address and sign in with a Google account can use the assistant, which spends your model quota (the free
  tier allows about 40 tickets a day), and the account in `ADMIN_EMAIL` sees Insights. Put a password in front of the tunnel.
  This ngrok version has no `--basic-auth` flag; use a traffic policy. Save this as a file OUTSIDE the repo, for example
  `%USERPROFILE%/ngrok-policy.yml`, with your own long password:
  ```yaml
  on_http_request:
    - actions:
        - type: basic-auth
          config:
            credentials:
              - "reviewer:choose-a-long-random-password"
  ```
  then start the tunnel with `ngrok http 4200 --traffic-policy-file %USERPROFILE%/ngrok-policy.yml` and give the reviewer the
  username and password separately from the link.
  This uses ngrok's `basic-auth` traffic-policy action. It was written from ngrok's documentation and not run here, because running it
  means opening a public tunnel; if ngrok rejects the file, check the action's current syntax in ngrok's traffic-policy docs.
- The data is synthetic, but the app signs people in and holds your `GROQ_API_KEY` on the server. Stop the tunnel (`Ctrl+C`) when you
  are done, and never tunnel a build that points at real customer data without a proper deployment.
- The help-centre MCP server can be tunnelled too: `make mcp-http` serves it over HTTP on :8765 behind the bearer token in
  `MCP_HTTP_TOKEN`, and `ngrok http 8765` publishes it (see `docs/MCP_CLIENT_GUIDE.md`).

### Using an outside MCP client

The help-centre search is exposed as an MCP server with one tool, `search_help_centre(query, policy_version?, top_k?)`.
Two ways to reach it:

- over HTTP: `make mcp-http` (needs `MCP_HTTP_TOKEN` in `.env`), then connect any MCP client to
  `http://127.0.0.1:8765/mcp` with the header `Authorization: Bearer <token>`;
- over stdio: `{ "mcpServers": { "help-centre": { "command": "python", "args": ["mcp_servers/help_centre_server.py"], "cwd": "/path/to/repo" } } }`.

The first start takes about 10 seconds while the embedding model loads. Step by step for three clients:
`docs/MCP_CLIENT_GUIDE.md`.

### Known limits (read before trusting a number)

- The judge's agreement with a human is **not measured** until a person labels at least 20 replies on the admin page **Label replies**; the report says NOT MEASURED until then.
- The free tier caps this model at 200,000 tokens a day, 1,000 requests a day and 8,000 tokens a minute. With the entitlement check and first search done in code (prefetch), a ticket uses about a quarter fewer tokens, but a full evaluation run can still reach the daily cap; it then stops, keeps the finished cases, and `--resume` continues the next day. See `deliverables/week12/cost_and_10x.md`.
- The corpus is templated, so retrieval scores are optimistic compared with real help-centre text.

## 1. Project Overview

This system answers billing questions and resolves support tickets by:

- **Ingesting** help-centre articles (PDF, Markdown, Word, Excel, plain text) into three local vector store collections
- **Retrieving** relevant chunks via hybrid search (BM25 + dense vector, fused by Reciprocal Rank Fusion)
- **Generating** grounded, cited answers via a cloud (Groq) or local (Ollama) LLM
- **Refusing** questions the indexed articles cannot answer
- **Resolving tickets** with a ReAct agent that calls billing tools via MCP servers
- **Tracking** every trace with Langfuse observability (optional)

## 9. Authentication

The app uses Google OAuth 2.0 for sign-in. On first login, the account matching `ADMIN_EMAIL` is granted the `admin` role; all other accounts receive the `user` role.

**To set up Google OAuth:**

1. Go to [console.cloud.google.com](https://console.cloud.google.com) > APIs & Services > Credentials
2. Create an **OAuth 2.0 Client ID** (Web application)
3. Add `http://localhost:4200` to **Authorized JavaScript origins**
4. Copy the Client ID into `.env` as `GOOGLE_CLIENT_ID`
5. Also paste the same Client ID into `frontend/src/app/components/login/login.component.ts`

JWTs expire after 7 days. The Angular auth interceptor attaches the token automatically on every request.

## 10. Chat Modes

The chat interface has two modes, selectable from the input bar:

### RAG mode (default)

Answers billing questions by retrieving relevant chunks from the knowledge base and generating a cited response. Uses hybrid retrieval (BM25 + dense vector, fused by RRF).

- If no relevant chunks are found, the system returns a friendly fallback rather than hallucinating.
- Sources can be expanded below each answer (article name + section heading + excerpt).

### Agent mode

Resolves support tickets using a ReAct loop. The agent calls billing tools in sequence until it has enough information to reach a verdict (approve / deny / escalate).

**Tools available:**
- `get_ticket` -- retrieves the ticket text, customer ID, and order ID
- `get_order` -- fetches purchase date, amount, and fulfilment status
- `get_customer_tier` -- returns the customer's tier and refund window
- `search_knowledge_base` -- runs a RAG search over the billing articles

The agent shows a summary of which steps it took and its final answer.

## 13. Chunking Strategies

Three strategies are built. The default is **structure-aware**.

| Strategy | Collection | How it works |
|---|---|---|
| **Structure-aware** | `billing_structure_aware` | Splits on `##` section headings; parses Markdown tables into one chunk per row |
| **Baseline** | `billing_baseline` | RecursiveCharacterTextSplitter (800 chars / 100 overlap) |
| **Semantic** | `billing_semantic` | Splits where cosine distance between sentence windows spikes |

## 14. Evaluation

### RAG evaluation (25-question golden set)

```powershell
python evaluation\run_eval.py
```

Runs 4 deterministic assertions and an LLM-as-judge across 25 labelled questions. Results are written to `evaluation/`.

### Agent trajectory evaluation

Access `/trajectory` (admin only) in the UI to run trajectory evaluation, apply mitigations, and test prompt injection defence.

### Langfuse traces

Every RAG call and agent run is traced in Langfuse when `LANGFUSE_PUBLIC_KEY` is set. Traces are also written locally to `evaluation/traces.jsonl` regardless of Langfuse availability.

## 16. CLI Usage

Ask a billing question directly from the terminal without the UI:

```powershell

```

```

profile migration is incomplete because a required field was not carried over
from the legacy platform.
```
